역할별 화면 구성과 사용 방법

가로형 페이지를 기준으로 왼쪽은 화면 구성(와이어프레임), 오른쪽은 사용설명입니다. 현재 시스템은 정적 홈페이지 + Express/MongoDB API로 동작하며, 로그인 역할은 상주(family)와 관리자(admin)입니다. 슈퍼바이저는 아직 코드에 없으며, 운영 필요에 맞춘 권장 역할 설계로 정리했습니다.

배포 URLincheon.onrender.com
스택HTML/CSS/JS + Express + MongoDB

제안 역할슈퍼바이저 (미구현)

시스템 흐름

브라우저 → 정적 페이지 (index / pages) → Express API (/api) → MongoDB

공개 홈페이지는 누구나 열람합니다. 상주·관리자는 /pages/member/login.html 통합 로그인 후 역할에 따라 상주 포털(/pages/member/*) 또는 관리자(/admin/)로 이동합니다.

왜 필요한가

현재는 관리자 1등급이 품목 단가·계정·정산을 모두 다룹니다. 병원/공단 운영에서는 현장 관리자와 감독(슈퍼바이저)을 나누는 편이 안전합니다.

  1. 조회: 빈소 이용, 주문, 문의, 정산 현황 열람
  2. 승인: 고액 주문·할인·사후정산 확정 승인 (선택)
  3. 감사: 요금/계정 변경 이력, 발인 정산 문서 점검
  4. 제한: 품목 단가·상주 계정 삭제·시드 데이터 초기화는 금지
구현 시 User.role에 supervisor 추가, requireSupervisor 미들웨어, 관리자 메뉴를 읽기/승인 전용으로 분기하는 방식이 적합합니다.

  • 상주 — 본인 장례 건만 예약·조회·문서

5. 정리 및 의견

현재 상태 평가 · 우선 개선안

한 줄 평가

공개 안내 → 상주 예약 → 관리자 정산으로 이어지는 실무형 구조가 이미 잘 잡혀 있습니다. 다만 역할이 admin/family 2단이라, 병원·공단 조직의 “감독” 니즈에는 슈퍼바이저(또는 최소 감사 로그)가 필요합니다.

잘 된 점

  • 통합 로그인으로 상주/관리자 진입 경로가 단순함
  • 빈소 이용 ↔ 상주 계정 연결, 주문·문서 출력까지 업무 흐름이 연결됨
  • 홈페이지 메뉴가 절차·서비스·조문·도움말·지원으로 체계적
  • 다국어(한/중/영)와 e하늘 연계로 현장 안내가 수월

보완하면 좋은 점

  • 슈퍼바이저 역할 또는 최소 “변경 감사 로그”
  • 관리자 메뉴가 많아 현장 직원용 “간편 모드(접수·승인만)” 분리 검토
  • 상주 첫 로그인 시 비밀번호 강제 변경·이용 안내 체크리스트
  • 모바일에서 관리자 메가메뉴 사용성 개선

권장 운영 순서

  • 1) 관리자: 빈소 이용 등록 → 상주 계정 발급
  • 2) 상주: 로그인 → 장례 예약 → 내 예약 확인
  • 3) 관리자: 주문 확정·사후정산 → 문서 출력
  • 4) (제안) 슈퍼바이저: 고액/할인/최종 정산 승인

바로 적용 가능한 의견

  • 지금은 슈퍼바이저 화면을 새로 만들기보다, 관리자 권한 분리(운영자/감독자)부터 설계하는 것이 효율적
  • 홈페이지는 게스트용 “안내”, 상주 포털은 “거래”, 관리자는 “운영”으로 역할을 명확히 유지
  • 설명서 파일: docs/시스템구성_및_사용설명서.html (가로 인쇄 지원)
